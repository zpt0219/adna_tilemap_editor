# 2-corner 崖面地形：做过、删了、以及为什么

> 日期：2026-08-08
> 性质：**事后记录**。一个建成又删除的子应用（`autotile_2corner`）的全部结论。
> 关联：[`AUTOTILE_SCHEMES.md`](AUTOTILE_SCHEMES.md)（三种方案的语义）、
> [`AUTOTILE_PATTERN_BAKE.md`](AUTOTILE_PATTERN_BAKE.md)（blob47 的烘焙链路）
> 参考素材：`assets/test4.png`（手绘，64×64，仓库外）

---

## 0. 一句话结论

**用 4 个角（4 bit）驱动的程序化场，在 16px 分辨率下画不出手绘质感的地形轮廓。**
试了三种场，全部失败。而单张手绘参考图里也提取不出可参数化的结构（三种拆解假设
都只有 67–73% 一致率）。所以「参数化生成 = 手绘质量」这条路在这个组合下是死的。

要么烘焙美术（精确但固定），要么**改变作者画什么**（见 §6）。

---

## 1. 建过什么

`autotile_2corner`，标准 Wang 2-corner（16 张图集），草地高台 + 小山坡崖面，
地形 B 输出透明。两种出图模式：

- **烘焙**：把 `assets/test4.png` 的 16 张图抽成索引表，运行时纯查表
- **距离场**：程序化生成轮廓

删除时状态：64 个测试通过，构建 / lint 干净。删除原因不是它坏了，是**距离场模式
达不到可用的美术质量，而烘焙模式除了改配色以外做不了结构变化**——后者用 Aseprite
就够了，工具没有存在价值。

保留的：`autotile_mixer` → `autotile_blob47` 的改名，以及 `start-local.mjs` 的
Windows 路由修复（见 §7.4）。

## 2. 唯一真正成立的模型

崖面的方向性——上边缘薄、下边缘厚——不需要按方向分情况写，一个表达式就够：

```
草地 = { F(p + (0, v)) ≥ r }
```

`F` 是到 A/B 边界的有符号距离场，`r` 是侵蚀半径，`v` 是抬升。
等价于**把地形 A 缩小 r、再整体向上抬 v**。厚度自动变成：

| 外法线 | 厚度 |
| --- | --- |
| 北 | `r - v` |
| 东 / 西 | `r` |
| 南 | `r + v` |

拟合 `test4.png`：**r=3.7, v=3.4，逐像素准确率 90.1%**。两个参数打到 90%。

### 2.1 接缝预算（这条是普适的，值得记住）

地形 A 是 A 角**对偶格**的并集（对偶格 = 以角为中心、边长一个瓦片的方块）。
瓦片内任意点到「非本瓦片 4 角」的对偶格距离都 ≥ T/2，所以场在 T/2 处截断就只
依赖这 4 个角——**这就是 16 张图足够的全部理由**。

抬升和噪声都把查询推向瓦片外，所以三者共享同一份预算：

```
r + v + 噪声幅度 ≤ T/2 − 0.5     （T=16 时是 7.5）
```

**实测是紧的**：和 = 7.5 时随机地图逐像素比对 0/48384 不一致，7.7 时 6 个，
8.5 时 80 个。参考图自己落在 7.1，正好在界内。

⚠️ 预算是**半个瓦片**，与分辨率无关。32px 买到的是分辨率，不是"崖面占比更大"。

### 2.2 崖面色阶

崖面**两端暗、中间亮**（这是它读起来像画的主要原因）：

- 紧贴草地下方 1px：84% 是最暗色（草檐投影）
- 中间：亮面，最亮色只占 8–11%（稀疏高光）
- 底部 2px：83–93% 最暗色（崖底描边）

两条暗边是**绝对宽度**（1px / 2px），不是崖高的比例。物理上它们本来就是常量
（屋檐投影、描边），而且比例模型在薄的北向边缘会缩成零，丢掉参考图确实画了的
那条 1px 暗线。

配色配方（HSV，`hue` 一律是**增量**不是绝对值）：

- 草地暗边：`hue +0.114, sat ×0.773, val ×0.724`
- 崖面每暗一级：`hue −0.036, sat ×0.92, val ×0.80`

色相向紫倒转，是"阴影发紫而不是单纯变暗"的来源。

## 3. 死路一：三种基础场都不行

| 场 | 结果 |
| --- | --- |
| 方格并集（对偶格 SDF） | 凹角自动圆滑、**凸角 90°**，8px 尺度上必然阶梯 |
| + `smin` 凸角圆滑 | 见 §3.1，上限太低，视觉上几乎无差别 |
| 核函数求和（metaball） | 地形内部被打出洞——核在角与角之间塌陷 |
| 归一化核（Shepard 插值） | 洞没了，但轮廓**比方格并集还方** |

### 3.1 凸角圆滑的两重限制

只在**相邻**角对之间做 `smin`（对角混合会越过截断半径，实测破坏接缝）。代价有两层：

1. `smin(a,b,k) = min(a,b) − h²k/4`，最多把距离压低 `k/4`，**要计入接缝预算**
2. 光有 k/4 还不够。瓦片只能混合自己 4 个角，而真实场会混合所有相邻格点对——
   这种缺失随 k 增长，与预算无关。60 组随机形状实测：**≤2.5 零失败，3 失败 1/60，
   4 失败 5/60**

而 k=2.5 的圆角，和 k=0 并排看**几乎无差别**。这条路投入产出极低。

### 3.2 根因：信息量

**输入 4 bit，输出 4096 像素。** 任何 4 bit 的光滑函数都不可能长得像手绘。
参考图好看是因为有人在 4096 个像素上做了逐一决定。这不是调参能解决的。

## 4. 死路二：手绘图里提取不出结构

想让烘焙的美术支持结构变化，就得把它拆成可参数化的部件。三种拆解假设全部不够：

| 假设 | 一致率 | 随机基准 |
| --- | --- | --- |
| 崖面可按列缩放 | 方向盲（见下） | — |
| 靠边 8 行由该边 2 个角决定 | 72.9% | 50.7% |
| 象限由「自身角 + 相邻 2 角」决定 | 67.1% | 51.0% |

**按列缩放为什么坏**：南向边上，一列里的崖面段就是崖面正脸，缩放它是对的；
但东西向边上，那段是**沿边界方向的竖条**，缩放等于把它沿自身长度拉伸，毫无意义。
所以调完崖高之后侧边样式就对不上了。方向盲是这个做法的死穴。

**72.9% 那条尤其关键**：它意味着一张瓦片无法推断出上方瓦片的草地长什么样，
所以「更高的崖面溢进下面那张瓦片」不可导出——崖面只能在瓦片下沿被裁掉。
同样也堵死了"用烘焙轮廓 + 算法重新挤出崖面"。

结论：**这位画师是把 16 张图当整体画的**，不是按可重组的部件画的。信息不在里面。

## 5. 烘焙确实能做到像素级精确

如果目标只是"和参考图一模一样"，烘焙是构造性成立的，且已验证：
解 PNG 后与发布代码的输出逐字节比对，**4096/4096 完全一致**。

两个实现要点：

- 每像素存**调色板索引**（本例 7 个：透明 / 草地 / 草地暗边 / 崖面 4 阶），
  这样换色不动形状
- 换色用**锚点重映射**：把"作者的锚色 → 用户选的颜色"这个 HSV 变换同样施加到
  每一档上。关键性质是**不改颜色时它是恒等变换**，精确性才不会被"顺便重新推导
  色阶"毁掉。直接从选中色推导色阶会算出 `#623946`，而作者画的是 `#5e3643`——
  差几个单位，对生成器无所谓，对像素级精确是致命的

重建方法（`assets/test4.png` 还在的话）：按 `WANG_LAYOUT` 槽位顺序切 4×4，
每块 16×16，逐像素映射到调色板索引即可。

## 6. 如果以后再捡起来

按推荐度排序。共同前提：**必须加信息，不能指望从单张图里提取**。

1. **改成画「象限」而不是画「整块」**——作者画每个角位置的 8 种象限配置（含对称
   可更少），工具拼装成 16 张，**接缝由构造保证**。某个象限画第 2 版就组合爆炸出
   大量互不相同且一定无缝的图集。画 2 套象限的工作量远小于画 2 套图集，产出却是
   组合级的。`AUTOTILE_SCHEMES.md` §4 指的就是这个粒度。
2. **内置瓦片编辑器 + 实时接缝检查**——画完一块立刻看到平铺效果，自动高亮角配置
   相容的邻居之间的错配像素。这是 Aseprite 做不了的部分。
3. **把崖面拆成独立图层**——别让一张 16px 瓦片同时装下草地和高崖。草地走 2-corner，
   崖面作为独立贴边条，高度自由（16/24/32）。这是唯一能让崖高真正自由的做法，
   也是多数游戏的实际做法。但它会改变图集格式，可能影响引擎。
4. **多套烘焙图 + 逐格随机**——最简单，但要多画整图，产出只线性增长。

## 7. 方法笔记（这部分最值得复用）

### 7.1 接缝证明

同一张随机角点地图渲染两遍——一遍按瓦片查表，一遍用整图全局场——要求逐像素相同。
如果某张瓦片需要 16 张图承载不了的信息，两者必然不一致。比"看着没缝"可靠得多。

### 7.2 我在测量上犯的错（三次，值得记住）

判断 `test4.png` 到底是图集还是示例地图，我反复了三次：

1. **"是示例地图"** —— 错
2. **"是图集"** —— 结论对，但依据是**被混淆的**：象限一致性 71.2% vs 掩码顺序
   55.5%。可那个布局本身是空间连续的，而图是一块居中的陆地，两者天然相关，
   和"是不是图集"无关
3. **"不是图集，因为 256 种切法都切不出全透明瓦片"** —— **假前提**。mask 0
   要求的是四个**角**为 B，不是整张空白；作者在那个空槽里画了个装饰小岛

**教训**：在检验"数据是否满足 X"之前，先确认 X 真的是假设**蕴含**的。三次里两次
是工具区分不了假设，一次是判据压根不成立。后者更隐蔽。

（另有一次更糟的：用"最佳剪影匹配"给瓦片定掩码，结果全指向 mask 15——因为全不透明
能匹配任何大部分不透明的瓦片。统计量必须能区分候选假设。）

### 7.3 先测量再猜系数

凸角圆滑的安全上限我猜了两次系数（"≤4 一律安全"、"k/4 就够"），两次都错。
第一次错在扫描时固定了参数配比，看不出它依赖配比；第二次错在漏了另一种破坏方式。
**随机化扫描**（60 组随机配比）才给出可信的 2.5。

### 7.4 顺带修掉的真 bug

`start-local.mjs` 在 Windows 上**六个子应用全部 404**：URL 路径被丢进
`path.normalize`，而 Windows 上它会把 `/` 改写成 `\`，导致所有
`pathname.startsWith('/app/')` 恒假。最阴的是 `/` 反而正常——它同样匹配失败，
但兜底路径正好拼出 `server/` 目录。改用 `path.posix.normalize`。Linux 部署不走
这条路径，线上不受影响。
