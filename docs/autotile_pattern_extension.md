# 纹理参数扩展分析：哪些纹理可加入 Scale / Density Slider

> [!NOTE]
> **状态（2026-08-09）**
>
> - **Phase 1 `ripple`：已上线。** `rippleScale` slider（2~8）已落地，并顺带新增了本文档未提及的 `ripple_diag`（45° 斜向水波），复用同一个参数。
> - **§4 `nonslip` 已程序化**，8px 原始尺寸逐字节复现原表，尺寸档 8/16/32px（只向上放大）。
> - **新增 `square`（正方形铺砖）**，复用同一套尺寸控制，最大档一格就是整个 tile。
> - **新增 `brick_bond`（程序化错缝砖）**，砖面用地形色、四个色阶分别是高光/阴影/横缝/竖缝。⚠ 需要把纹理密度拉到 100% 才能看到四层，见《brick_bond》。
> - **§6 几何铺装：三个全部已程序化并带尺寸控制。** `isometric` / `octagonal` 在 32px 逐字节复现原表；`hexagon` 起初复现不了，后来按用户的判断把手绘的散点并入边线，就落到了同一个模型上（见《hexagon：把散点并入边线之后》）。
> - **Phase 2 `water`：已实现、已实测、已还原。** 程序化 Voronoi 边线做完并通过了全部客观指标，但用户试用后判断「比手绘还是差了很多感觉」，整体回退。**`water` 现在仍然是 baked 32×32 手绘表**，没有间距控制。代码保留在 git stash，见文末《Phase 2 事后记录》。

## 背景

已完成 `cells` 的 `cellScale` 参数（2×2 ~ 6×6 Voronoi 网格密度）。现在分析所有 22 个纹理算法，看哪些还能通过引入一个新参数来扩展其表现力。

---

## 纹理分类与参数化可行性分析

### ✅ 可参数化的纹理（推荐加入 Slider）

#### 1. `ripple` — 水面波纹 · 横向短划

- **当前实现**：`rippleField`（[patternTexture.ts](../autotile_mixer/src/utils/patternTexture.ts)）使用 `perX = 4`（4 个水平单元跨 32px → 每条约 8px 宽的横向相关性）和 `perY = 32`（每行独立）。
- **参数化方案**：`rippleScale` slider 控制 `perX`，范围 **2 ~ 8**。
  - `perX = 2` → 每条波纹约 16px 宽，非常稀疏宽大的波浪
  - `perX = 4` → 当前默认，中等密度
  - `perX = 8` → 每条仅 4px，非常稠密的细波纹
- **可行性**：⭐⭐⭐⭐⭐ 极简改动，只需将 hardcoded `perX = 4` 改为参数传入
- **语义**：`波纹密度 / Ripple density`

#### 2. `water` — 水面边线

- **当前实现**：`WATER` baked table（[patternTexture.ts](../autotile_mixer/src/utils/patternTexture.ts)）是一个固定的 32×32 像素表，边线位置已经写死。
- **参数化方案**：不能简单缩放 baked table。但可以改为**程序化生成**：用 Voronoi 边界来画水面边线（类似 cells 但只画边界线不填充），`waterScale` 控制边线之间的间距。
  - 或者更简单的方案：保留 baked table，但用一个 `lineSpacing` 参数控制 **amount 阈值的非均匀采样** — 即稀疏时只保留部分边线。
- **可行性**：⭐⭐⭐ 如果改为程序化 Voronoi 边线则高度可行但工作量大；如果只是控制密度则效果有限
- **语义**：`边线间距 / Line spacing`

> [!IMPORTANT]
> `water` 使用的是 baked 32×32 pixel art table，无法像 `cells` 那样简单地改变一个 `per` 参数来缩放。要真正控制"边线之间空间的大小"，有两条路：
>
> **方案 A（推荐）**：将 `water` 改为程序化 Voronoi 边界线 + 随机散点，用 `waterScale` 控制 Voronoi cell 数量（类似 cells 但只画 grout 线不填充 interior）。这样边线间距直接由 cell 密度决定。
>
> **方案 B**：保留 baked table 不变，只用 slider 控制 amount/阈值。这仅控制"有多少边线可见"，无法真正改变边线之间的物理间距。

*（方案 A 已实施并还原，见文末。当前是「两条路都没走」：baked 表原样保留，没有间距控制。）*

#### 3. `cells` — 多边形细胞 ✅ 已完成

- 已有 `cellScale` slider（2 ~ 6），控制 Voronoi 网格密度。

---

### ⚠️ 理论上可参数化但改动较大的纹理

#### 4. `nonslip` — 交叉防滑纹 ✅ 已完成

- **当前实现**：`NONSLIP` baked table，32×32 但实际是 8×8 的重复图案。
- **参数化方案**：如果改为程序化生成（交叉对角线网格），可控制网格间距。但 baked table 改程序化开销大。
- **可行性**：⭐⭐ baked table 限制了参数化

**结果（2026-08-09）**：已程序化，**在原始 8px 尺寸逐字节复现原表**（0/1024 不符），表已删除、改作测试 oracle，尺寸档 8 / 16 / 32px。评估里的「⭐⭐ 开销大」判断偏保守 —— 它其实是这批里最规整的一个，见文末《nonslip：两条短划加阴影》。

#### 5. `brick_wall` / `cobbles2` / `brick_floor` — 各种砖

- **当前实现**：全部是 baked pixel art tables。
- **参数化方案**：如果改为程序化（running bond 算法），可控制砖块大小。但这些纹理的像素级细节（砖面上的明暗变化、风化痕迹）是 baked art 的核心价值，程序化很难还原。
- **可行性**：⭐ 不建议改动，baked art 的质感是手绘的

#### 6. `hexagon` / `isometric` / `octagonal` — 几何铺装 ✅ 已完成

- **当前实现**：baked 32×32 tables。
- **参数化方案**：这三个的几何结构理论上可以程序化生成（六边形网格、菱形网格、八边形网格），然后用 scale 参数控制大小。
- **可行性**：⭐⭐⭐ 程序化生成这些几何图案并不复杂，但需要从零重写

**结果（2026-08-09）**：三个全部程序化，表全部删除、改作测试参照，都带「铺装块尺寸」radio。`isometric` / `octagonal` **在 32px 逐字节复现原表**（各 0/1024）；`hexagon` 第一次尝试失败（最好 131/1024 且平台），把手绘的散点并入边线后成功，与合并后的原图差 32/1024 且差异性质无害。详见文末两节。

### ❌ 不适合参数化的纹理

| 纹理 | 原因 |
|------|------|
| `weave` | 16×16 baked art，菱格编织图案的像素级细节无法缩放 |
| `paving` / `paving3` / `paving5` | 32×32 baked art，乱砌石板的不规则排列是手绘的核心价值 |
| `stone_floor` | 32×32 baked art，不规则石板间缝的位置和形状是手绘的 |
| `breeze_block` | 32×32 baked art，镂空砖的孔洞位置是固定的 |
| `field` / `rubble` | 32×32 baked art，草地/碎石的分布是手绘有机形态 |
| `white` / `blue` / `ordered` | 这三个共用 `patternNoise` 模块的 `sample()` 函数，其密度已经由 `amount` 参数控制 |

# 几何铺装：两个成功一个失败（2026-08-09）

和 water 那次方向相反 —— 这三个是**规则几何**，程序化本来就该能精确重现；water 的问题恰恰是「太规则」。所以这次把验收标准定成**逐字节一致**，而不是统计相似：做到了就等于零观感风险地白拿一个尺寸参数，做不到就不做。

| 纹理 | 结果 | 32px 下与原表不符 |
|---|---|---|
| `isometric` | ✅ 程序化，表已删 | **0 / 1024** |
| `octagonal` | ✅ 程序化，表已删 | **0 / 1024** |
| `hexagon` | ⚠️ 第一次失败，见下一节的后续 | 最好 131 / 1024（12.8%），且平台 |

新增「铺装块尺寸」radio。档位必须整除 32 **且**是偶数像素，否则 `octagonal` 那条「每格只画一次」的共享边线会落在半像素上。可用档位按纹理而定，见 `geoScalesFor`。

## 新增 `square` — 正方形铺砖（2026-08-09）

不是原三个之一，是新加的纹理，直接建在同一套 `geoScale` 机制上，所以没有新参数、没有新状态，只多一个下拉项。

三层：**grout（1px，露地形本色）→ frame（1px，色阶中段）→ face（纹理色）**。frame 是一个常量 `SQUARE_FRAME_RANK = 2`，改成 0 就变成不带内框的纯网格。

两个刻意的设计：

- **grout 只画在每格的两条边**，不是四条。相邻方格共享它，网格因此在任何尺寸下都是 1px；四条边都画会让每对邻居之间变成 2px。
- **相位跟随原始 seed，不是加盐后的 seed**（其他两个铺装用加盐相位，因为那是它们手绘表的原始相位，动了会破坏逐字节 oracle）。这样 seed 0 时 grout 正好落在格子边界上，最大档的方格就是整个 tile。用加盐相位的话偏移是 (17, 29)，预览里方格会被切在中间 —— 接缝仍然正确，但看起来像 bug。

实测（浏览器，全铺 A 的画板）：grout 列在 x = 31, 63, 95, 127…，行同理，**pitch 精确 32，对齐 tile 边界**。16px / 8px 档分别是 16 和 8 的 pitch。

变异测试三项全中：grout 画四条边、frame 塌进面色、格子尺寸忽略 scale。

## 新增 `brick_bond` — 程序化错缝砖（2026-08-09）

参考手绘的 `BRICK_WALL`（16×8 砖、1px 灰缝、逐层错半砖），但**色阶分配是反过来的**：手绘用 rank 3 画砖面，这个用 **rank 0 画砖面**，也就是砖就是地形色，四个色阶全部用来画砖上面的东西。

| 色阶 | 语义 | 位置 |
|---|---|---|
| 0 | 砖面 | 地形本色，占多数 |
| 1 | 高光 | 砖内顶边 1px |
| 2 | 阴影 | 砖内底边 1px |
| 3 | 横向灰缝（bed joint） | 每层之间 1px，整行不断 |
| 4 | 竖向灰缝（head joint） | 1px，比横缝深一级 |

两个方向的灰缝给不同色阶，是为了让墙读出深度而不是平网格；想要统一灰缝就把 3 和 4 设成同色。**T 形交叉处横缝赢**，这跟手绘一致（它的横向灰缝是整行不断的），否则每条层线都会被竖缝切成虚线。

尺寸 32×16 / **16×8（默认，手绘的比例）** / 8×4。

> [!WARNING]
> **8×4 档不画高光。** 4 行里一行灰缝、一行高光、一行阴影就占了三行，砖面只剩 1 行（实测占比 22%），整块砖全是斜面。这个尺寸下省掉高光是像素画的常规做法，代价是色阶 1 在该档位用不到 —— 取色器会自己置灰。

### ⚠ 默认密度会压掉色阶，需要拉到 100%

`rankToShade` 会把 rank 乘上纹理密度，而密度默认是 40%：

| rank | 语义 | 40% 下的色阶 | 100% 下 |
|---|---|---|---|
| 1 | 高光 | `round(0.4)` = **0，完全消失** | 1 |
| 2 | 阴影 | 1 | 2 |
| 3 | 横缝 | 1（与阴影撞色） | 3 |
| 4 | 竖缝 | 2 | 4 |

所以默认只看到 2 种颜色，色阶 3/4 的取色器显示「用不到这一级」。**把纹理密度拉到 100% 后四层全部分离**，实测四色各自独立（#458bd7 / #5097e4 / #5aa3f2 / #65afff），四个取色器全部可用。

这是这一族纹理共有的行为、不是本纹理特有的（`square` 的 rank 2/4 在 40% 下同样压成 1/2），但 `brick_bond` 用了相邻的 1,2,3,4 四级，所以受影响最明显 —— 四个语义层在同一个 ramp 上，没有拉开的余地。

要在默认密度下就看到四层，只有给这个纹理单独的 amount 语义，选项有两个：**（a）** 选中它时把密度默认设为 100%（复用 `naturalGeoScale` 那套「按纹理的默认值」机制）；**（b）** 让密度改为控制细节层数（低 = 只画灰缝，高 = 加上斜面），灰缝始终满强度。两者都未实施，等决定。

变异测试四项全中：去掉错层偏移（变成通缝）、竖缝在交叉处赢、去掉底部阴影、砖面给一个色阶而不是地形色。

## nonslip：两条短划加阴影（2026-08-09）

用户读图的判断完全正确：**两种重复的线段带阴影**，而且用现有 4 色阶就能完美拟合。

结构（8×8 严格周期，只用 rank 0 / 2 / 4）：

```
..#+..++     # = rank 0 暗芯（露地形本色）
.##+....     + = rank 4 阴影
##+.....     . = rank 2 底色
#+......
+...#...
....##..
....+##.
.....+#+
```

两条短划：一条沿 `x+y` 向左下，一条沿 `x−y` 向右下，各是 **2px 暗芯 + 1px 阴影**。关键一点：**两条的阴影都落在各自「垂直向下」那一侧**（A 的在右下、B 的在左下）—— 同一个光源方向，这才让两者读成压在金属板上的人字纹，而不是两笔无关的划痕。所以不能把 B 写成 A 的镜像：镜像会把「下」翻成「上」。

写成两个对角坐标上的带状条件后，**0/1024 逐字节命中**，一次通过。

### 放大方式：线宽不缩放（已渲染两版后选定）

参数全部用 `u`（单元尺寸 / 8）表达，但**线宽刻意不随 u 变**：暗芯恒 2px、阴影恒 1px，只有划长和间距随尺寸增长。

两版都渲染出来比较过：等比放大在 32px 会变成很粗的斜向楔形，失去防滑纹的质感，而且划尾的收口会从渐收变成一个方块。测试 `nonslip keeps its lines 2px thin` 锁住这个决定。

### 两个新增的通用机制

尺寸控件是几个纹理共用的，但它们不是同一个尺寸画的，于是加了两个按纹理查询的函数：

- **`naturalGeoScale(texture)`** — 该纹理被绘制时的尺寸（nonslip = 8px，其余 = 32px）。切换算法时把档位重置过去，这样每个纹理选中时都是它原本的样子。否则档位停在 32px 时一选 nonslip 就是四倍粗，完全不像它。
- **`geoScalesFor(texture)`** — 该纹理可用的档位。nonslip 到 8px 为止、**只能向上放大**：它的划长、间距和两条划的位置都是单元的整数八分之一，4px 会落在半像素上。列表里直接不给这一档，而不是钳制 —— 钳制会留下一个点了没反应的按钮。

变异测试四项全中：线宽跟着尺寸放大、删掉第二条划、删掉阴影、忽略原始尺寸。

## hexagon：把散点并入边线之后（2026-08-09）

上一节的结论是「拟合不出来」。用户看了原图后指出：**那些散点可以合并到边线里，这样 hexagon 也跟其它规则多边形一个思路**。这不是换算法，是换验收目标 —— 而它成立。

按「每个面内部非主色的像素归入 rank 0」构造合并后的目标图，hexagon 立刻落到和其余铺装完全相同的模型上：**最近格心 + 到六面墙的距离**，描边阈值 0.5px。

### 结果：32/1024，但差异性质无害

| | 数值 |
|---|---|
| 与合并后原图不符 | 32 / 1024（3.1%） |
| 其中面色 vs 面色的错位 | **0** —— 全部是「描边 vs 面色」 |
| 色调统计 | **完全相同**：140 描边 / 221 / 221 / 442 |

也就是说 16 个像素对等互换，没有任何区域上错色。差别只在**斜边阶梯落在哪一个像素**：手绘的是不规则的 1,1,2,2,1,2,2 阶梯，生成的是均匀交替 —— 对一个叫「规则六边形」的纹理，均匀那个反而更对。

测试把不符数**精确锁在 32**，并断言每一处差异必有一侧是描边、且色调统计一致。任何模型改动都会让这个数字动。

### 一个不显眼但会跨接缝出错的坑

面色按 (列, 行) 奇偶查表，但**不能直接用行号的奇偶**：向右移 32px 是 `(c, r) → (c+2, r−1)`，`r` 的奇偶会翻转，于是同一个六边形从接缝两侧到达时会拿到两种颜色。加上 `floor(c/2)` 项才能穿过 wrap 保持不变 —— 修之前实测 52 个像素颜色错。

另一个坑：候选格心必须**从像素反推格号**，不能围绕原点扫固定范围。格子变小后固定范围覆盖不到瓦片的大部分，那些像素会退化成实心描边 —— 我第一次的探针就是这样，16px 档整个右半边糊成一片黑。

### 尺寸档

32 / 16 / 8px，不给 4px：再对半就只剩 2px 的六边形压在 1px 描边下，全是边没有面。变异测试四项全中：行奇偶查表、固定范围搜格心、描边加倍、砍掉第三个面色。

## 两个成功的几何解

**`isometric`**：两套交错的菱形中心（一套着色、一套本色），共享边界描黑。度量 `(|dx|/W + |dy|/H) * 32`，格子边界恒定落在 32，所以只有容差需要随尺寸变。

> [!WARNING]
> **容差必须随尺寸放大，这是个静默 bug。** 度量的梯度随铺装块数增长，容差固定为 1 时描边宽度变成 1/n 像素 —— 实测在 16px 和 8px 档**整条描边完全消失**，铺装渲染成两块平色、中间没有缝。测试 `isometric keeps its outline one pixel wide` 就是拦这个的。

**`octagonal`**：格心取在 `S/2 - 1` 而不是 `S/2 - 0.5`，这样直边正好落在整像素的格子边界上、而不是两像素之间。相邻八边形因此共享一条描边、由外侧那格画一次 —— 这个不对称性是原始手绘art里就有的，也是为什么代码里直边和倒角是分开判断的。

## `hexagon` 第一次为什么失败

它的斜边上有一圈「tip」像素，取的是比面色低两级的色（面色 3 → tip 1，面色 4 → tip 2；面色 2 的 tip 变成 0，于是并入描边网络，那个六边形因此只有 221px 而不是 231px）。

把 rank 摊成 (面色, 边方向, 到边界距离) 的函数来拟合：**纵向接缝很干净**（距离 0 → rank 0，之后就是面色），但**斜边上 rank 0 / tip / 面色混在同一个距离桶里**，不是距离的函数。扫了 20 组阈值组合，最好 131/1024 不符就平台了。那些 tip 是手工摆的。

所以当时 hexagon 保留 baked 表、不给尺寸控制，并且明确否掉了「32px 手绘 + 16px/8px 程序化」的混合方案 —— 程序化版本在同一尺寸下差 12.8%，风格可见地不同，切尺寸会同时换风格，那正是 water 那次被否掉的模式。

**这个结论后来被推翻了**，靠的不是更聪明的拟合，而是改了目标 —— 见下一节。

## 原表没有丢

`ISOMETRIC` 和 `OCTAGONAL` 两张表现在住在 `patternTexture.test.ts` 里，作为 oracle：生成器必须逐像素复现它们，否则测试失败。**它们是那份手绘数据仅存的副本，不要当成冗余清掉。**

变异测试四项全中：容差不随尺寸放大、倒角阈值 off-by-one、格心挪到 S/2-0.5、第二套菱形格不偏移 —— 各自被对应测试捕获。

## 这个落差本身是本次最重要的记录

> 它们量的都是**局部**性质：单条线弯不弯、细胞多扁、点多密。手绘表里没被任何指标捕捉到的东西，很可能是**全局构图**——哪里疏哪里密、哪几个细胞特别大、线怎么成组地走向。Voronoi 天然是均匀的：每个细胞差不多大、每条线差不多长、疏密处处一致。均匀正是「一眼看出是生成的」的根源，而它不出现在任何一个局部指标里。
>
> **下次再试，先找一个能区分「均匀」和「有构图」的指标**（比如细胞面积的方差、线密度在 tile 内的空间自相关），否则会重复这次的过程：指标全绿，观感不过关。

## 三个被实测推翻的技术结论（这些仍然有效）

即使实现被还原，这三条是可复用的知识，重来一次会踩同样的坑。

### 一、`f2 - f1` 不能用来画线

本文档《实现思路》第 2 步写的「只在 `f2 - f1 < threshold` 处画线」是错的，照做会得到**块**而不是线。

该差值只在两个最近种子分居像素两侧、且夹角够大时才正比于到边界的距离。自由浮动的种子经常挨得很近，那里梯度塌陷，固定阈值把「线」胀成几像素宽的板。实测：per=3 时 21% 的 tile 被涂成连片色块，per=6 时 41%。**`cells` 用的正是这个判据 —— 它那条偏粗的 grout 就是同一现象**，如果哪天要给 cells 收细边线，这里是原因。

正确做法：求**到中垂面的精确距离**，且必须对 3×3 邻域内**所有**种子取最小值。只取第二近的那个会在 Voronoi 顶点附近高估距离，在每条线上打出可见缺口。

### 二、「Voronoi 边线太直」这个前提不成立

为消除「直线感」实现了域扭曲。三个独立指标测下来，warp 开与关**没有差别**：

| 指标 | warp=1 | warp=0 |
|---|---|---|
| 5 像素直段占比 | 25% | 25% |
| 转折密度 | 47% | 48% |
| PCA 弯曲残差 | 1.47px | 1.53px |

原因是根本没有直线可修：32px tile 里 2~6 个细胞，一条 Voronoi 边只有 5~16px 长，还没显出直线感就撞上下一个交点。未加 warp 的输出本来就和手绘表一样弯（1.53 vs 1.42）。

warp 唯一测得出的贡献是把闭合的网轻微撕开（断头数 0 → 约 5，手绘表 17）。

### 三、拉长格子必须同时收紧种子抖动

只把格子按轴拉长**完全无效**。种子原本在整个格子内自由浮动，box 16×4.6 时横向自由度 ±8px 大于纵向间距 4.6px，纵向相邻的种子实际主要是横向错开的，中垂线变成斜的，扁平度被自己的抖动洗掉 —— 3.5:1 的 box 只做出 1.14 的细胞。

抖动系数是个权衡，两个指标反向：调大 → 比例掉回方形；调小 → 比例上去但网格变规则，弯曲残差从 1.42 掉到 1.05。0.4 是交叉点。

另外，各向异性必须做在**种子分布**上、距离仍用像素空间的欧氏距离；改成拉伸度量会让线宽随方向变化，扁细胞的横边比竖边粗。

## 如果要第三次尝试

不要再从 Voronoi 出发调参数——这次已经把它调到了局部指标的上限。可考虑的方向：

- **非均匀的种子分布**：先用低频噪声决定哪片区域细胞大、哪片小，再放种子。直接攻击「均匀」这个根因。
- **完全换模型**：手绘水面更像「横向长条 + 竖向短连接」的手工构图，而不是任何距离场的等值线。参考 [[measure-before-assuming-texture]] 里那条「不要用距离场复现手绘art」的结论——最佳平滑拟合只有 88.84%，771 对像素证明不可达。
- **接受 baked**：22 个纹理里 16 个是 baked art，这是这个项目一贯的取舍（见 [user-ui-preferences] —— hardcode the art，runtime 只做查表）。要更多水面变体，画第二张表比生成一张更可控。
